# Coding Guidelines

This guide establishes the coding standards, patterns, and principles for developers working in this codebase.

---

## 1. Core Principles

### SOLID Principles
- **S**ingle Responsibility: A widget should only present UI. A controller should only manage UI state. A repository should only orchestrate data.
- **O**pen/Closed: Design components to be open for extension but closed for modification. Customize widgets using properties instead of editing their source files.
- **L**iskov Substitution: Abstractions (e.g. `Repository` interfaces) must be fully replaceable by their implementations without breaking client code.
- **I**nterface Segregation: Create small, focused interfaces rather than single bloated contracts.
- **D**ependency Inversion: High-level widgets and business logic controllers must depend on abstract repository interfaces, not concrete API data sources.

### Composition over Inheritance
- Build complex UI layouts by nesting small, focused widgets (like `AppCard`, `AppText`, `AppSpacing.gapMd`).
- Avoid creating custom subclass hierarchies of `StatefulWidget` or `StatelessWidget`.

### Separation of Concerns
- **No Business Logic inside Widgets**: Widgets should only call methods on controllers or listen to provider states. Never invoke Dio clients, SQLite transactions, or parse raw JSON inside widgets.
- **Immutable States**: All presentation states MUST be immutable. Use `@freezed` state classes.

---

## 2. Naming Conventions

### File & Folder Naming
- Use `lower_snake_case` for all directories, files, assets, and route paths.
- Feature directories must be plural, e.g. `features/`. Single feature modules should be singular: `features/authentication/`.

### Class & Variable Naming
- Use `PascalCase` for all class names, including widgets, entities, models, and controllers.
- Use `camelCase` for variables, properties, methods, and providers.
- Custom widget names must be prefixed with `App` if globally shared (e.g. `AppPrimaryButton`). Private feature widgets should be prefixed with the feature name (e.g. `AuthHeader`).

### Provider Naming
- Suffix provider variables with `Provider` to make dependencies clear:
  ```dart
  final authRepositoryProvider = Provider<AuthRepository>(...);
  final authControllerProvider = StateNotifierProvider<AuthController, AuthState>(...);
  ```

---

## 3. State Management Rules (Riverpod)

- **Use AsyncNotifier / Notifier**: Prefer newer Riverpod `Notifier` or `AsyncNotifier` structures (which can be autogenerated via `@riverpod` annotations) for dynamic states.
- **Keep States Focused**: Create separate controllers for different pages or logic blocks (e.g. one for `LoginState`, one for `RegisterState`) rather than a single massive state class.
- **Avoid Global Listeners**: Always scope listeners inside target presentation widgets using `ref.listen` instead of spawning long-lived root event loops.

---

## 4. File Sizing, Clean-up & CLI Commands

- **File Size Cap**: Keep widget files under **300 lines of code**. If a screen gets larger, slice it into smaller private widgets (e.g. `_ProfileHeader.dart`) stored inside the feature's `presentation/widgets/` folder.
- **Remove Dead Code & Keep Comments Clean**: Never commit commented-out code blocks or unused package imports. Keep the code clean by avoiding comments when generating or writing code, unless they are extremely important.
- **Format Code**: Always format the code before committing using `fvm dart format lib/`.
- **Linter Obedience**: Ensure zero warnings or info markers are highlighted by Dart analyzer.
- **Always Use FVM**: Prefix all Flutter/Dart operations with `fvm` (e.g., `fvm flutter pub get`, `fvm flutter analyze`, `fvm dart format .`). Do not run raw `flutter` or `dart` commands.
